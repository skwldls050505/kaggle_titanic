# Titanic baseline 진단과 다음 실험 가이드

기준: titanic_1.ipynb의 저장된 실행 결과, titanic_eda.ipynb의 학습 부분 분석, submission_result_1.csv.
이 문서는 기존 결과를 해석한 것이다. 새로운 모델 학습이나 교차검증은 이번 분석에서 수행하지 않았다.

## 1. 현재 baseline의 의미

- train.csv 916행 중 687행 학습 / 229행 validation, seed 42와 stratify 사용.
- 세 모델을 비교해 CatBoost를 선택한 후 전체 916행에 다시 학습했다.
- 제출 파일에는 393명의 생존 확률이 들어간다. 제출 CSV는 모델 자체가 아니라 모델의 예측 결과다.
- 아래 AUC는 전체 train 재학습 모델의 독립 평가가 아니라 687행으로 학습한 후보 모델의 holdout 평가다.
- test 정답과 대회 점수는 없으므로 실제 대회 일반화 성능까지 판단할 수 없다.

현재는 과소적합보다 과대적합을 먼저 점검할 상황이다. 과소적합은 학습 데이터에서도 충분히 배우지 못하는 상태인데, 세 모델 모두 학습 AUC가 높다.
단, AUC 차이 몇 이상이면 과대적합이라는 보편적 기준은 없다. 학습 점수는 원래 낙관적이고, 229행 검증 표본의 변동도 포함된다.
CatBoost가 LightGBM보다 약 0.006 높지만 한 번의 분할로 확실히 우월하다고 결론 내리지는 않는다.
AUC 0.900은 정답률 90%라는 뜻이 아니라 양성/음성의 점수 순위를 얼마나 잘 구분하는지 나타내는 지표다.

## 6. 다음 실험의 순서

### 1순위: 비교 기준을 먼저 안정화

현재 holdout을 유지해 작은 실험들을 같은 조건으로 비교한다. 그 뒤 후보 몇 개만 같은 StratifiedKFold 5개 분할에서 비교해 평균 AUC와 표준편차, 각 fold의 차이를 기록한다.
각 fold 안에서 전처리 객체를 새로 만들고 학습 fold에만 fit해야 한다. 전체 데이터 전처리 후 CV를 하면 누수다.
현재 validation도 모델 선택에 이미 사용했다. 반복적으로 확인할수록 점수가 낙관적으로 될 수 있고, CV 역시 최종 성능 보증은 아니다.
동일 가족/티켓 승객의 정보 공유가 염려되면 이후 그룹 분할을 추가 점검한다. 이는 예측 대상이 새로운 그룹인지에 따라 의미가 달라지는 별도 검증이다.

### 2순위: CatBoost의 과대적합 완화

기존 피처를 고정한 채 트리 깊이를 줄이는 실험, 정규화를 강화하는 실험을 각각 한다.
예를 들어 실제 기본 설정을 확인한 후 depth를 한 단계 줄이거나 l2_leaf_reg를 한 단계 높인다. 동시에 여러 파라미터를 바꾸지 않는다.
Train AUC가 내려가더라도 Validation AUC가 유지/상승하면 좋은 방향일 수 있다. 둘 다 하락하면 규제가 지나칠 수 있다.
훈련 회차별 train/validation AUC를 기록하면 어느 시점부터 검증 성능이 정체/하락하는지 볼 수 있다. early stopping도 후보지만 평가셋 재사용의 낙관성을 염두에 둔다.
최종 전체 train 재학습에는 선택한 회차 수를 사용한다. test를 eval_set에 넣지 않는다.

### 3순위: 결측 정보의 추가 가치

1. baseline + HasCabin만 비교한다.
2. baseline + AgeMissing만 비교한다.
3. 개별 실험에서 개선이 반복될 때 조합을 비교한다.

이 두 변수는 현재 전처리에서 정보가 사라지는 지점을 보완한다. 개선될 것이라는 결론이 아니라 검증할 가설이다.

### 4순위: 관계 피처와 제거 실험

- gender×pclass: 기존 변수의 상호작용을 명시적으로 표현했을 때 도움이 되는지 확인.
- FamilySize 또는 IsAlone 중 하나 제거: 현재 피처의 추가 가치 확인.
- 가족 규모 구간화: 작은 범주를 묶는 대신 세부 정보가 사라지는 손익 확인.
- Fare/FamilySize: 실제 공동 티켓 인원이 아니므로 개인당 실제 운임이라고 부르지 말고 비율 피처로 취급.
- Title: 이름에서 추출할 수 있으나 희귀 범주 처리와 작은 표본 문제 때문에 후순위.

### 이후: 모델 비교와 앙상블

전처리/검증이 안정된 뒤 LightGBM, XGBoost를 같은 조건에서 재비교한다. 확률 평균 앙상블은 각 모델의 오류가 다를 때 도움이 될 수 있으며, 모델 수가 많다고 자동 개선되지는 않는다.
현재 단계에서는 대규모 탐색, 무조건적인 class weight 증가, 임계값 0.5 조정부터 시작하지 않는다. 제출 확률을 유지하는 한 분류 임계값 변경은 ROC AUC를 개선하지 않는다.

## 7. 초보자용 코드 작성 가이드

- baseline 노트북/제출 파일을 기준으로 고정하고 다음 실험은 별도 버전으로 작성한다. 공통 모듈까지 바뀌면 baseline 동작도 바뀌므로 변경 버전 또는 스냅샷을 남긴다.
- 데이터 로딩과 검증 단계는 지금처럼 명시적으로 작성한다. 반복되는 fit/transform만 common에 둔다.
- 실험 하나마다 “가설 → 변경 한 가지 → 같은 분할 평가 → 채택/보류 이유”를 적는다.
- 제출 파일은 실험마다 만들 필요가 없다. validation 기준으로 채택된 설정만 전체 train 재학습 후 다음 파일명으로 저장한다.

HasCabin은 cabin 삭제 전에, AgeMissing은 나이 치환 전에 만들어야 한다.
기존 전처리 순서의 큰 제목을 유지하려면 결측치 처리 단계에서 원본 마스크를 보관하고 Feature 생성 단계에서 사용한다.

```python
# 결측치 처리 단계: 원본에서 마스크를 보관
age_missing = X_train["age"].isna().astype(int)

# 이후 기존 결측치 처리 수행
# X_train_clean = ...

# Feature 생성 단계: 같은 행 index를 유지해 결합
X_train_clean["AgeMissing"] = age_missing
```

실제 구현에서는 이 로직을 TitanicPreprocessor의 학습/검증/test 경로에 일관되게 적용한다. 한 DataFrame만 고쳐서 제출 때 컬럼이 달라지지 않게 한다.
행마다 계산하는 isna, 가족 합계는 별도 fit이 필요 없지만 중앙값, 최빈값, encoder는 학습 데이터에만 fit한다.

- Train 상승 / Validation 하락: 과대적합 악화 가능성.
